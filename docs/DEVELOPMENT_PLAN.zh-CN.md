# Windows 灵动岛开发计划

日期：2026-11-09。当前阶段：完成选型与源码调研，尚未实现应用。

## 1. 首版的目标

先做一款每天能用的音乐灵动岛，优先保证 Windows 版 Apple Music 的播放控制和歌词体验。首版完成并实际使用后，再开发番茄时钟、日历等功能。

首版包括：顶部胶囊；歌名、歌手、封面；播放/暂停、上一首、下一首；跟随播放进度切换的一行歌词；鼠标展开音乐面板；托盘退出。没有音乐时显示安静的待机状态。首版不做逐字卡拉 OK、机器翻译、完整播放器、账号登录或自动更新。

“能显示 Apple Music 歌词”和“能取得 Apple 官方歌词”是两个目标：前者可以使用匹配到的其他歌词源；后者需要验证本地缓存可读性与歌曲身份。产品内要能查看来源，不能将外部歌词标成 Apple 原生歌词。

## 2. 用大白话理解程序结构

| 部分 | 负责什么 | 首版选择 |
| --- | --- | --- |
| 界面 | 画胶囊、封面、文字和按钮 | Rust + egui/eframe |
| Windows 接口 | 找到播放器、读取信息、发送控制命令 | windows crate，使用 Windows 媒体会话接口 |
| 歌词来源 | 找到这首歌对应的带时间歌词 | Apple Music 本地缓存，外部来源作为可关闭的备用 |
| 歌词时钟 | 根据播放时间决定显示哪句 | 独立的 Rust 逻辑，处理暂停、跳转、循环和切歌 |
| 窗口与托盘 | 置顶、缩放、多屏、鼠标点击和退出 | Windows 原生窗口接口与托盘 |

Rust 是实现语言；egui 负责绘制；Windows 接口负责连接系统。Rust 本身不保证界面漂亮、动画流畅或耗电低，这些都需要设计和实测。

暂定沿用上游的技术路线，减少同时学习多套框架的成本。具体依赖版本在 M1 的可编译工程中确定并锁定；此次调查记录的是上游版本，不等于决定永远沿用这些版本。

## 3. 如何使用上游代码

采用“新仓库、按模块迁移”的方式。保留 origin 指向本项目，upstream 指向 Daozai，用固定提交核对迁移来源。添加 upstream 只是方便对照，不会自动合并两个项目的提交历史。

优先参考/迁移的部分：`smtc.rs` 的媒体信息与控制、`lyrics.rs` 的歌词结构与 LRC 解析、`anim.rs` 的动画，以及 `native.rs` 的窗口处理。`app.rs` 已混合多个功能，不整文件搬入首版。

上游的 egui/eframe 有本地补丁，迁移窗口相关代码时必须一起评估，不能只复制 Cargo.toml 后假定表现相同。先复现最小窗口，再按遇到的问题引入必要补丁。

每次复制或改写代码，都在 THIRD_PARTY_NOTICES.md 记录：原仓库、提交号、文件、许可、本地落点和修改。仅参考方案也要与实际导入区分。保留需要的版权声明和许可文本；不沿用 Daozai 的产品名、Logo、捐赠入口或服务账号配置。

## 4. Apple Music 歌词实现路线

已确认 Windows 媒体元数据接口没有歌词字段。Daozai 被检查的版本没有 Apple Music 专用本地歌词适配器；这并不证明用户当前问题只由这一项引起，实际还可能有元数据、匹配或网络问题。

先做只读诊断，验证当前 Apple Music 版本是否提供歌名、歌手、专辑、时长、时间轴和可用控制，再确认是否存在可读的歌词缓存。已找到的开源参考实现会在 Apple Music 包的 `AC/INetCache` 下寻找 `ttmlLyrics*.json`，读取其中的 TTML。该路径与格式是兼容性线索，需要本机验证，不能当成 Apple 的稳定公开接口。

歌词选择顺序：

1. 用户为当前歌曲明确绑定的本地 LRC（如已提供）。
2. 已验证歌曲身份的 Apple Music 本地 TTML 缓存。
3. 用户启用在线查词时，使用 LRCLIB；其他来源待覆盖率实测后再决定。
4. 只有纯文本则显示为无时间歌词；没有可靠匹配则显示“暂无歌词”。

缓存匹配优先使用可靠的歌曲 ID；媒体接口不保证提供 Apple 曲目 ID。必要时通过歌名、歌手、专辑、版本和时长解析目录候选，并验证是否唯一。联网目录查询与联网查词一起可关闭。只靠“最新缓存文件”或“时长差不多”不能直接采用，不能把 Live、Remix、翻唱和原版混在一起。

缓存可能尚未生成，可能需要在 Apple Music 中打开歌词面板；具体触发条件在 M2 验证。没有缓存时仍应能显示歌曲和控制播放。不得读登录令牌、修改 Apple Music 文件、注入进程或下载音频。

切歌立即清除旧歌词；后台任务带上会话身份和曲目代次，迟到的旧请求不能覆盖新歌。暂停时停止推进歌词；恢复、跳转、循环、睡眠唤醒后重新校正时钟。网络错误、未找到、纯音乐和格式错误分别处理，断网不能被永久记成“无歌词”。

首版主验收平台定为 Windows 11 x64。Windows 10 兼容性单独列为未验证，完成相应实机测试后再宣称支持。先提供便携版，安装器和自动更新后续开发。

## 6. 高质量的具体标准

完整场景见 [TEST_PLAN.md](TEST_PLAN.md)。首版至少满足：

- 选择 Apple Music 后，浏览器视频不会抢走按钮的控制目标。
- 控制请求失败时能反馈；不把“请求已发送”当成播放器已执行。
- 切歌、暂停、拖动进度、循环之后，歌词不会持续显示旧歌或自行继续前进。
- 无词、纯音乐、断网时，播放按钮仍可用，界面不卡住。
- 后台磁盘和网络任务不阻塞界面；窗口静止或隐藏时降低重绘频率。
- 中文、英文、长歌名和高 DPI 下可读；透明区域不挡住下面窗口的点击；控制按钮不抢键盘焦点。
- 记录空闲和播放时的 CPU、内存、句柄与网络访问；连续运行后不持续增长。

不把“能画出一颗胶囊”当成首版完成。后续添加功能会更方便，但多屏、缩放、状态切换和资源占用仍需要持续验证。

## 7. Git 与更新记录

`main` 保存经过对应检查的里程碑。当前 main 可以只有经过检查的文档；有应用后，合入的功能必须通过格式、静态检查、构建和自动测试。涉及 Windows/Apple Music 的功能另外记录实际客户端验收结果。

每个功能建立短期分支，一次完成一个可验收变化。并行开发互不依赖的功能时使用 git worktree；不必提前建立多个空分支，也不需要常驻 develop。通过测试后才推送该批变化，创建 PR，再合入 main。后续以 GitHub Actions 检查远端同一提交。变更与测试证据随提交进入 CHANGELOG 和 PR。

禁止上传听歌历史、真实歌词缓存、登录数据、密钥和本机诊断输出。测试歌词使用自编的短句，真实歌曲只在本地验收记录其结果。日常操作见 [CONTRIBUTING.md](../CONTRIBUTING.md)。
